# linear-actions

Post comments and perform workflow automations on Linear issues directly from GitHub Actions. The first supported command, `comment`, posts a comment to a Linear issue and optionally deduplicates identical messages.

## Usage

```yaml
jobs:
  notify-linear:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Comment on Linear issue
        uses: your-org/linear-actions@v1
        with:
          api-key: ${{ secrets.LINEAR_API_KEY }}
          issue-key: ABC-123
          body: "Preview available at https://env.example.com"
          dedupe: true # optional, defaults to true
```

## Inputs

| Name        | Required | Default | Description |
|-------------|----------|---------|-------------|
| `api-key`   | Yes      | —       | Linear API key with access to the issue. |
| `issue-key` | Yes      | —       | Linear issue identifier (e.g. `ENG-42`). |
| `body`      | Yes      | —       | Comment text to post. |
| `dedupe`    | No       | `true`  | Skip posting when the issue already contains an identical comment. |
| `command`   | No       | `comment` | Reserved for future sub-commands. |

## Behavior

1. Looks up the issue UUID from the public key (e.g. `ABC-123`).
2. When `dedupe` is enabled, fetches existing comments and skips if the exact `body` already exists.
3. Posts the comment through the Linear GraphQL `commentCreate` mutation.

## Development

```bash
npm install
npm test          # run unit tests
npm run build     # compile TypeScript and bundle with ncc
```

GitHub Marketplace submissions should include the `dist/` artifacts generated by `npm run build`.

## Releasing

This repo uses [semantic-release](https://semantic-release.gitbook.io/) to version and publish automatically. Follow the Conventional Commits spec (e.g., `feat: add dedupe flag`, `fix: handle missing issue`) so the CI can infer semver bumps. Merge those commits into `main` and the `Release` workflow will run tests, rebuild `dist/`, create the changelog entry, push tags/commits, and publish the GitHub release/Marketplace update. You can also trigger the same flow locally via `npm run release` (requires repo write access).

### Conventional Commit refresher

Format each commit as `type(scope?): short description`, where `scope` is optional. Common types:

- `feat`: adds new user-facing behavior (bumps **minor**)
- `fix`: patches a bug (bumps **patch**)
- `chore`, `docs`, `test`, etc.: maintenance-only (no release unless combined with other types)

Add `!` after the type or include `BREAKING CHANGE: ...` in the body to trigger a **major** release. Keep descriptions imperative and under ~70 chars; add details or references in the body.
